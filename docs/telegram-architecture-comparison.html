Message-centric, not message-only.

A source-backed comparison of Telegram’s publicly documented model and the current Frappe WhatsApp Core, Hub and relay design—with a practical path to simplify our DocTypes without losing CRM, audit, routing or business-integration capabilities.

Primary Telegram sources only 48 Core DocTypes audited 18 Hub DocTypes audited Local source review

Executive verdict

Do not rebuild Telegram’s presumed database.

Telegram proves a compact public object model, but its production server schema is private.

Telegram explicitly calls message its main object. It still models chats, users, files, folders, read cursors, permissions and update state separately. “Everything is a message” is a useful design instinct—not a factual description of one giant messages table.

Our application should become message-centric: one immutable communication timeline with small projections around it. It should not force transport, CRM, workflows, campaigns, calls and audit evidence into one polymorphic record.

Evidence boundary

Telegram publishes clients, TDLib, its protocol and API—but not the production server code. This report compares verified API/client semantics, not an invented Telegram server ERD.

Verified Telegram model

What “message-centric” actually means

Verified

Messages are the main timeline object

  • Every message belongs to a chat and has an identifier unique inside that chat.
  • Content is a typed union: text, photo, document, call/service event and many more.
  • History is cursor-paged by message ID in reverse chronological order.
  • Replies and topics point to message IDs instead of copying message bodies.
Not true

Telegram does not expose “only messages”

  • Chat is a separate object with last message, positions, unread counts and read cursors.
  • User, group, file, folder, permission and notification state are separate objects.
  • Updates are ordered state transitions; clients maintain caches and repair sequence gaps.
  • Media has stable file identity plus local and remote availability metadata.
Efficient projection

Unread state is cursor-first

Telegram exposes last_read_inbox_message_id and unread_count on the chat/update model. That makes the common unread query proportional to chats, not to the full message × reader history.

Event-driven cache

Clients mutate local projections

New messages, last-message changes, chat positions, read cursors and files arrive as targeted updates. The UI updates the affected cached object instead of refetching and rebuilding every list.

Identity aliases

The alias concept is necessary; the duplicate storage is not.

Why multiple identifiers are legitimate

One WhatsApp person may arrive as a phone number, a Meta business-scoped user ID, a parent business-scoped ID, or a rotated provider ID. Keys can also be channel-scoped. Removing aliases would recreate the wrong-recipient and duplicate-chat bugs this layer was built to prevent.

What is messy today

Phone aliases exist both as rows in WhatsApp Core Identity Alias and inside Identity.attributes.phone_aliases. Identity Link and Party Binding then provide two partially overlapping ways to attach the same identity to business records.

Recommended canonical identity model

Identityidentity_id

Stable internal person/group anchor, display profile, state and preferred key.

Identity Keyprovider · scope · kind · value

Unique lookup table for Phone, BSUID, Parent BSUID and Group ID. Replaces “Alias”.

Business Bindingidentity · doctype · record · role

One lifecycle-aware link to a Frappe business object. Replaces Link/Party overlap.

Resolve inbound addresses only through Identity Key. Resolve outbound destination from the conversation’s channel-scoped key. Never choose a recipient from display text, a random linked DocType or the last identity row that happens to match.

Why not put calls, comments and system events directly into Core Message?
Renderable call start/end or assignment changes may have a timeline message projection. The authoritative call session, recording lifecycle, internal comment permissions and mutable assignment state still need typed records. A timeline entry is a view of the event—not automatically the only source of truth.
Why keep Core Event when Message already stores the webhook result?
Core Event is the idempotent inbox and audit envelope. One provider event can create or update a message, identity, conversation, call, group receipt and business handler. Deleting it would mix delivery reliability with the user-visible projection and make replay/debugging unsafe.

Authoritative ownership

One fact, one owner, many projections

Hub · control plane
  • Meta credentials and WABA/account authority
  • Connected-site routes and subscriptions
  • Template authority and sync orchestration
  • Operator-level platform diagnostics
Relay · transport plane
  • Webhook verification and normalized work items
  • JetStream delivery, retries, dead letters and quotas
  • Graph API transport
  • No CRM identities, teams or business records
Core · tenant data plane
  • Identities, conversations, messages and local media
  • Operator reads, teams, folders and comments
  • Tenant-local projections, search and UI
  • Never owns Meta credentials
Business apps · domain plane
  • Partner, Member, Customer, Ticket and Invoice truth
  • Presentation and typed action hooks
  • No duplicate WhatsApp transport or message tables
  • Bindings reference Core identity; Core does not import domains

Recommended next move

Clean it without breaking or dropping data

Freeze the contract

Document the canonical keys, owners and retention of every current DocType. Add contract tests before changing schema.

Add new canonical projections

Create Identity Key, Business Binding and Core Media alongside existing tables. Backfill in bounded, resumable batches.

Dual-read, single-write

Write only the new model; temporarily read new-first with a legacy fallback. Emit metrics whenever fallback is used.

Verify referential parity

Compare counts, hash key sets, orphan links, recipient routing and sampled conversation timelines before cutover.

Cut over by capability

Identity lookup first, business binding second, media third. Do not combine this with UI or relay changes.

Retire only after observation

Stop legacy writes, observe zero fallbacks, archive tables, then remove old DocTypes in a later release.

Non-negotiable architecture decisions

✓
Provider ID is not the Frappe document name.

Use compact internal names and indexed unique external keys.

✓
Message history is immutable-first.

Status and content edits are explicit projections; original ingress remains auditable.

✓
Hot unread queries use cursors.

Exact per-message reader history is loaded only for a visible bounded window.

✓
Realtime events carry changed objects.

Append/update the affected chat or message; do not reload complete lists.

✓
Derived tables are rebuildable.

Summaries, insights, counts and search documents must not become transport dependencies.
